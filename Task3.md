# Лабораторная работа: переносное резервное хранилище

# Вариант 3

## Общая идея

Разработать консольное приложение для создания и обслуживания резервного хранилища на выбранном пользователем устройстве.
В качестве устройства может использоваться внешний диск, USB-накопитель, карта памяти или другая доступная файловая система.

При создании хранилища приложение формирует на выбранном устройстве специальный файл-контейнер. В этот контейнер сохраняются выбранные пользователем файлы и информация, необходимая для обнаружения последующих изменений.
При повторном подключении устройства приложение должно сравнить текущее состояние исходных файлов с состоянием последней резервной копии и предложить добавить в хранилище новые и изменённые данные.

---

# 1. Управление приложением

Приложение должно управляться через текстовые команды или меню.

Минимальный набор операций:

1. Создать резервное хранилище на выбранном устройстве.
2. Открыть существующее хранилище.
3. Показать сведения о хранилище.
4. Настроить список резервируемых файлов и каталогов.
5. Проверить наличие изменений.
6. Добавить обнаруженные изменения в хранилище.
7. Просмотреть сохранённые версии.
8. Восстановить файлы.
9. Проверить целостность хранилища.
10. Перезагрузить конфигурацию.
11. Завершить работу.

Пример командного интерфейса:

```text
> create
> open
> info
> sources
> scan
> backup
> versions
> restore
> verify
> reload
> exit
```


# 2. Создание и открытие хранилища

При создании нового хранилища пользователь должен:

* выбрать доступное устройство или каталог;
* задать имя файла хранилища;
* указать название хранилища;
* выбрать, требуется ли шифрование;
* выбрать способ хранения ключа;
* определить первоначальный список резервируемых файлов и каталогов.

Пример:

```text
> create

Доступные устройства:

1. E:\ — USB Drive
2. F:\ — External SSD

Выберите устройство: 1
Название хранилища: Personal Backup
Имя файла [backup.store]: personal-backup.store
Использовать шифрование? [да/нет]: да

Способ хранения ключа:
1. Сохранить ключ рядом с программой
2. Показать ключ и не сохранять его

Выберите способ: 2
```

Приложение не должно перезаписывать существующий файл хранилища без явного подтверждения пользователя.
Для открытия существующего хранилища пользователь должен выбрать устройство и файл-контейнер.
Если хранилище зашифровано, приложение должно запросить ключ доступа.

После открытия приложение должно показать основную информацию:

```text
Хранилище: Personal Backup
Файл: E:\personal-backup.store
Шифрование: включено
Источников: 4
Последняя резервная копия: 2026-09-14 18:30
Сохранённых версий: 7
```

---

# 3. Настройка резервируемых данных

Пользователь должен иметь возможность управлять списком файлов и каталогов, включённых в резервное копирование.

Для каждого источника необходимо хранить:

* исходный путь;
* признак включения вложенных каталогов;
* список исключений;
* состояние источника;
* дату последнего успешного резервного копирования.

Пользователь должен иметь возможность:

* добавить файл или каталог;
* изменить параметры источника;
* удалить источник из списка;
* временно отключить источник;
* просмотреть все настроенные источники.

Пример:

```text
Источники резервного копирования:

1. C:\Users\Student\Documents
   Вложенные каталоги: да
   Исключения: *.tmp, cache, node_modules
   Состояние: доступен

2. C:\Users\Student\Pictures
   Вложенные каталоги: да
   Исключения: thumbnails
   Состояние: доступен

3. D:\Projects\course
   Вложенные каталоги: нет
   Исключения: *.log
   Состояние: недоступен
```

Пользователю необходимо сообщить, какие источники не удалось проверить.

---

# 4. Конфигурационный файл

Настройки приложения должны храниться в отдельном конфигурационном файле.

Формат конфигурационного файла выбирается разработчиком. Например, JSON, YAML или TOML.

Пример конфигурации:

```json
{
  "logFile": "backup.log",
  "keyDirectory": "keys",
  "defaultContainerName": "backup.store",
  "checkOnStorageOpen": true,
  "confirmBeforeBackup": true,
  "confirmBeforeRestoreOverwrite": true,
  "maximumVersionsPerFile": 10,
  "hashAlgorithm": "SHA-256",
  "defaultExclusions": [
    "*.tmp",
    "*.log",
    "cache",
    "node_modules"
  ]
}
```

В конфигурации должны задаваться как минимум:

* путь к файлу журнала;
* каталог для сохраняемых ключей;
* имя файла хранилища по умолчанию;
* необходимость автоматически проверять изменения после открытия хранилища;
* необходимость подтверждать добавление изменений;
* необходимость подтверждать перезапись файлов при восстановлении;
* максимальное количество сохраняемых версий одного файла;
* способ проверки целостности файлов;
* стандартные правила исключения.

Настройка максимального количества версий должна влиять только на старые версии отдельных файлов. Последняя сохранённая версия не должна удаляться.

---

# 5. Обнаружение и сохранение изменений

После открытия хранилища приложение должно сравнить исходные данные с последним сохранённым состоянием.

Необходимо обнаруживать как минимум:

* новые файлы;
* изменённые файлы;
* удалённые файлы;
* переименованные или перемещённые файлы, если это возможно определить;
* недоступные источники;
* файлы, которые невозможно прочитать.

Результат проверки должен выводиться до изменения хранилища:

```text
Обнаружены изменения:

Новые файлы: 5
Изменённые файлы: 3
Удалённые файлы: 2
Недоступные файлы: 1
Общий объём новых данных: 148 МБ
```

Пользователь должен иметь возможность просмотреть список изменений и подтвердить их добавление.
При сохранении изменений приложение должно создать новую версию состояния хранилища.

Новые и изменённые файлы добавляются в контейнер. Для удалённых исходных файлов в новой версии фиксируется факт удаления, но предыдущие сохранённые данные не должны немедленно уничтожаться.

Если файл изменился во время выполнения резервного копирования, приложение должно сообщить об этом и не считать его успешно сохранённым.

После завершения операции необходимо вывести результат:

```text
Резервное копирование завершено.

Добавлено файлов: 5
Обновлено файлов: 3
Отмечено удалённых файлов: 2
Пропущено файлов: 1
Записано данных: 148 МБ
Версия хранилища: 8
```

---

# 6. Версии и восстановление

Хранилище должно сохранять несколько состояний резервируемых файлов.

Для каждой версии необходимо хранить:

* номер или уникальный идентификатор;
* дату и время создания;
* список добавленных, изменённых и удалённых файлов;
* результат выполнения операции;
* необязательный комментарий пользователя.

Пример:

```text
Версии хранилища:

8   2026-09-14 18:30   +5  ~3  -2   Рабочая копия
7   2026-09-10 20:15   +1  ~8  -0
6   2026-09-02 12:40   +12 ~0  -1   Перед обновлением системы
```

Пользователь должен иметь возможность восстановить:

* полное состояние на момент выбранной версии;
* последнюю сохранённую версию.

При восстановлении пользователь выбирает каталог назначения.

Если в каталоге назначения уже существует файл с таким именем, приложение должно действовать в соответствии с конфигурацией:

* запросить подтверждение;
* пропустить файл;
* перезаписать файл.

---

# 7. Шифрование и ключ доступа

При создании хранилища пользователь должен иметь возможность включить шифрование.

Если шифрование включено, содержимое контейнера не должно быть доступно без правильного ключа.

Должны поддерживаться два режима работы с ключом.

## Сохранение ключа рядом с программой

Приложение создаёт отдельный файл ключа в каталоге, заданном конфигурацией.

Пользователь должен быть предупреждён, что потеря каталога с программой или файла ключа сделает хранилище недоступным.

Файл ключа не должен сохраняться на том же устройстве внутри резервного контейнера.

## Передача ключа пользователю

Приложение показывает ключ пользователю и предлагает сохранить его самостоятельно.

Пример:

```text
Ключ доступа к хранилищу:

BK7F-3QPM-Y8VA-H2NX-6RKC

Программа не будет сохранять этот ключ.
Без него открыть хранилище будет невозможно.

Подтвердите, что ключ сохранён: да
```

После подтверждения программа не должна сохранять показанный ключ в конфигурации, журнале или других служебных файлах.

При открытии такого хранилища ключ должен вводиться пользователем.

Приложение не обязано восстанавливать потерянный ключ.

В журнал не должны попадать:

* ключи;
* части ключей;
* расшифрованное содержимое файлов;
* другие данные, позволяющие открыть хранилище.

# 9. Мониторинг и журналирование

Приложение должно вести журнал своей работы в отдельном файле.

В журнал необходимо записывать:

* запуск и завершение приложения;
* загрузку и проверку конфигурации;
* обнаружение доступных устройств;
* создание и открытие хранилища;
* неудачные попытки открытия зашифрованного хранилища;
* добавление, изменение и удаление источников;
* начало и завершение проверки изменений;
* количество обнаруженных изменений;
* начало и завершение резервного копирования;
* количество успешно и неуспешно обработанных файлов;
* создание новой версии;
* восстановление файлов;
* проверку целостности;
* обнаружение повреждений;
* ошибки чтения и записи;
* неизвестные команды;
* внутренние ошибки приложения.

Пример журнала:


В журнал не должны записываться:

* содержимое резервируемых файлов;
* ключи шифрования;
* расшифрованные данные;
* полный пользовательский ввод, если он может содержать ключ.

Журнал должен дополняться при каждом запуске, а не перезаписываться полностью.

---

# 10. Проверка конфигурации и обработка ошибок

Перед началом работы приложение должно проверить конфигурацию.

Необходимо обнаруживать как минимум следующие ошибки:

* путь к журналу не указан;
* каталог для ключей не существует и не может быть создан;
* максимальное количество версий меньше единицы;
* указан неподдерживаемый способ проверки целостности;
* правило исключения имеет неправильный формат;
* конфигурационный файл имеет неправильный формат.

Приложение также должно корректно обрабатывать следующие ситуации:

* введена неизвестная команда;
* команда недоступна в текущем состоянии;
* выбранное устройство отключено;
* на устройстве недостаточно свободного места;
* файл хранилища уже существует;
* файл хранилища отсутствует;
* файл хранилища повреждён;
* введён неправильный ключ;
* файл ключа отсутствует;
* источник резервного копирования отсутствует;
* отдельный файл невозможно прочитать;
* исходный файл изменился во время копирования;
* файл хранилища невозможно прочитать или изменить;
* каталог восстановления недоступен;
* восстановленный файл уже существует;
* журнал невозможно открыть или изменить;
* конфигурацию невозможно перезагрузить.

Некорректный пользовательский ввод и ошибки отдельных файлов не должны приводить к аварийному завершению всего приложения.

---

# 11. Ограничения задания

В рамках этой лабораторной работы не требуется:

* самостоятельно разрабатывать криптографические алгоритмы;
* автоматически исправлять повреждённое хранилище;
* восстанавливать потерянный ключ;
* создавать облачное хранилище;
* передавать данные по сети;
* синхронизировать несколько компьютеров;
* выполнять резервное копирование по расписанию без запуска приложения;
* отслеживать изменения файлов в реальном времени;
* создавать загрузочное устройство восстановления;
* создавать графический интерфейс;
* поддерживать одновременную работу нескольких пользователей;
* копировать заблокированные системные файлы;
* сохранять права доступа и другие специфичные для операционной системы атрибуты.

Приложение решает задачу создания переносного резервного хранилища, добавления новых версий файлов и восстановления сохранённых данных.
